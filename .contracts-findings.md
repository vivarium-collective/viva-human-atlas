# Contracts convention — investigation findings

## 1. Registering named bigraph-schema types

Pattern (from `pbg_biomodels/__init__.py` + `pbg_biomodels/types.py`):

- A workspace defines one or more plain-dict `TYPES_DICT`s mapping type name ->
  either a field-schema dict (`{"field": "type_str", ...}`) or a bare type string
  (e.g. `"map[list[float]]"`).
- Field values use bigraph-schema type syntax as plain strings: `string`,
  `integer`, `float`, `list[X]`, `map[X]`, `tree`, `maybe[X]`. Nested named types
  are referenced by name (e.g. `"organs": "list[matched_organ]"`).
- Registration: `core.register_types(TYPES_DICT)` inside a `register_types(core)`
  function, called from `build_core()` (`pbg_biomodels/core.py` calls
  `register_biomodels_types(core)` — actually `register_types` from the package)
  *and* the package's own top-level `register_types` (so external callers doing
  `from pkg import register_types; register_types(core)` also get them, e.g.
  workbench's registry-priming path that doesn't go through `build_core()`).

Applied to viva-human-atlas: added `viva_human_atlas/types.py` with
`VIVA_HUMAN_ATLAS_TYPES` + `register_workspace_types(core)`, wired into BOTH
`viva_human_atlas/__init__.py::register_types` (after delegating to
`pbg_biomodels.register_types`) and `viva_human_atlas/core.py::build_core()`
(after `register_biomodels_types(core)`).

## 2. Process/Step descriptions

Confirmed in `bigraph_schema/edge.py` (`Edge` base class, which `Process`/`Step`
extend via `process_bigraph.composite`):

- `description = ''` class attribute — canonical markdown/LaTeX description.
- `describe()` method returns `self.description or inspect.getdoc(type(self)) or ''`
  — i.e. explicit `description` wins, else falls back to the class docstring.
- `contract = None` class attribute — an optional **structured superset**
  (`bigraph_schema.contract.ProcessContract` or an equivalent plain dict), with
  fields `summary`, `description`, `inputs` (dict: port name -> description
  string), `outputs` (dict: port name -> description string), `config`, `math`,
  `symbols`, `assumptions`, `references`. `resolve_contract(instance)` merges a
  declared `contract` with the `description`/docstring (contract wins for
  authored fields; unset `summary`/`math`/`description` are parsed out of the
  flat `description` string).
- **Per-port descriptions ARE supported** — via `contract["inputs"][port]` /
  `contract["outputs"][port]`, NOT a schema `_description` field. Real working
  example: `viva_munk/processes/pressure.py` sets
  `Pressure.contract = {'summary': ..., 'inputs': {'agents': '...'}, 'outputs':
  {'agents': '...'}, 'assumptions': [...]}` as a **module-level attribute
  assignment after the class body** (not inside the class), presumably to keep
  the class definition itself lean and put the "documentation" pass at the
  bottom of the file. I followed this exact pattern.

Consumption confirmed in `vivarium-workbench`:
- `lib/process_docs.py::_describe_class` calls the real `describe()` on an
  uninitialized instance (`cls.__new__(cls)`) and sets `node['doc']` in the
  composite-state doc — this is what the Explorer's inspector shows as
  "Description" for a process/step node.
- `env_worker.py::_pd_contract_for_node` calls `bigraph_schema.contract.resolve_contract(cls)`
  and attaches the resulting dict (including `inputs`/`outputs` per-port maps)
  as `_contract` on the node — this is what would drive any per-port
  description surfaced by the Explorer/loom.

So both class-level `description`/docstring AND per-port `contract.inputs`/
`contract.outputs` are real, consumed conventions — not speculative.

## 3. How loom / the Composite Explorer read port types

`vivarium_workbench/lib/composite_resolve.py::resolve_composite` builds the
payload consumed by the Explorer (`GET /api/composite-resolve` /
`composite-state/*.json` in a published bundle). The `state` document embeds
each process/step's wiring; the actual **port types** come from
`process_bigraph.Composite(...).serialize_schema()` (invoked internally along
the `_live_generator_state` -> `build_composite_state` path when there is no
committed `default_state_ref`/artifact) — this schema is what shows a port's
declared type string.

**Empirical proof** (built the live `hra-reference-organs` generator via
`Composite({'state': doc['state']}, core=core).serialize_schema()`)
BEFORE the change:

```json
"reference_organs": "list[tree[node]]",
"load_step": {
  "_inputs": "node",
  "_outputs": "reference_organs:list[tree[node]]",
  ...
}
```

i.e. today the store's type is the fully-opaque `list[tree[node]]` — loom's
semantic zoom has nothing to key off beyond "it's a list of blobs". Once
`HRAReferenceOrgansStep.outputs()` declares `{"reference_organs":
"list[reference_organ]"}` and `reference_organ` is a *registered* named type
with real fields, the same store's declared type becomes
`list[reference_organ]` and the type is resolvable to its field schema
(`ref_organ_id`/`organ`/`uberon`/`sex`/`asset_url`, each a leaf `string`), which
is exactly the structure loom's semantic zoom needs to expand a "closed" node
into its typed children instead of showing an opaque leaf. Confirmed after
implementation (see `.contracts-report.md` for the after-JSON).

## Plan for Phase 2 (types to add)

- `reference_organ`: `{ref_organ_id: string, organ: string, uberon: string, sex: maybe[string], asset_url: maybe[string]}`
- `cell_type_term`: `{cl: string, count: integer}`
- `anatomical_term`: `{term: string, count: integer}`
- `matched_organ`: `{organ: string, uberon: maybe[string]}` (nested inside `biomodel_do.organs`)
- `biomodel_do`: `{biomodel_id: string, name: string, organs: list[matched_organ], provenance: tree}`
- `organ_to_models`: `map[list[string]]` (Uberon CURIE -> biomodel-id list)

`BioModelsSearchStep.outputs()`'s `model_ids: list[string]` is left as-is (a
list of bare ID strings is already a meaningful primitive type, not an opaque
`tree`); it gets a description/contract only.
